Préparation Orale — Points de friction examinateurs
====================================================

Voici les 10 points qu'un jury technique pourrait soulever, avec pour chacun :
le constat, la réponse factuelle articulant besoin business fictif vs impératifs
techniques, et le compromis assumé.


1. Credentials en dur dans .env
--------------------------------

Constat : admin/portfolio123, airflow/airflow visibles dans le repo.

Réponse :
- Business : Projet de certification, pas de données sensibles réelles (données
  publiques Binance). Aucun utilisateur final, aucune donnée personnelle.
- Technique : En production, on utiliserait un vault (HashiCorp Vault, AWS Secrets
  Manager). Le .env.example documente les variables requises sans valeurs.
- Compromis : Accepté sciemment — le coût d'un vault pour un démonstrateur local
  dépasse le bénéfice. Le .env n'est pas commité en production (.gitignore).


2. Annualisation : trading_days_per_year = 365
----------------------------------------------

Constat : 365 jours pour la crypto (marchés 24/7), mais la même valeur est
appliquée quelle que soit la granularité des candles.

Réponse :
- Business : Le besoin est de comparer des portefeuilles, pas de fournir des
  métriques auditables par un régulateur. L'important est la cohérence relative
  entre stratégies, pas la valeur absolue.
- Technique : Pour des candles journalières (cas par défaut), 365 est correct
  pour la crypto. Pour des candles 1 minute, il faudrait 525 600. La config
  interval pourrait piloter dynamiquement le facteur d'annualisation.
- Compromis : Le pipeline tourne en daily par défaut. Le cas 1-minute est un
  scénario de démonstration streaming, pas le flux principal d'optimisation.


3. Ratio de Sharpe anormalement élevé (~8.0)
--------------------------------------------

Constat : Un Sharpe > 3 est suspect en finance. 8.03 suggère un bug ou un biais.

Réponse :
- Business : Ce projet démontre une infrastructure de données, pas un modèle de
  trading viable. Le Sharpe est un indicateur parmi 30+ métriques exposées.
- Technique : Le Sharpe élevé vient de (a) une période de 30 jours trop courte
  (pas de crise capturée), (b) l'optimisation in-sample sans coûts de transaction,
  (c) l'absence de contrainte de position (short selling autorisé). Le backtest
  walk-forward corrige partiellement ce biais (out-of-sample).
- Compromis : Augmenter period_days et activer les contraintes de poids
  (/portfolio/constrained) donne des Sharpe réalistes (~0.5–1.5). La page
  "Cost Analysis" intègre frais et slippage.


4. Delta Lake : code mort
-------------------------

Constat : src/storage/delta.py implémenté (280 lignes, 20 tests), mais
config.toml utilise storage_backend = "parquet".

Réponse :
- Business : Le besoin initial est un lac de données performant. Parquet remplit
  ce rôle. Delta Lake répond à un besoin d'évolutivité (ACID, time travel,
  schema enforcement).
- Technique : L'implémentation est complète et testée. Elle est activable par un
  changement de config (storage_backend = "delta"). L'ADR-006 documente le
  raisonnement. Le pattern Storage ABC + factory permet de switcher sans toucher
  au pipeline.
- Compromis : En production avec des données critiques, Delta Lake serait le
  défaut. Pour la certification, Parquet suffit et évite la dépendance deltalake
  (optionnelle).


5. PySpark : « distribué » mais local[*]
-----------------------------------------

Constat : Le code PySpark tourne en mode local avec 2 Go de driver memory.
Pas de cluster.

Réponse :
- Business : Le volume de données (51 symboles × 30 jours ≈ 1 500 lignes) ne
  justifie pas un cluster. PySpark est là pour démontrer la compétence C8 (big
  data) et la capacité à scaler.
- Technique : Le code Spark est identique en local et sur cluster — seul le
  SparkSession.builder.master() change. Le Dockerfile.spark permet le déploiement
  sur un cluster (Kubernetes, EMR). Les window functions et aggregations utilisées
  sont les mêmes patterns qu'en production distribuée.
- Compromis : Dimensionner l'infra au volume réel. Un cluster pour 1 500 lignes
  serait du sur-engineering. La valeur ajoutée est dans le code Spark idiomatique,
  pas dans le cluster.


6. dbt : chemins relatifs fragiles
-----------------------------------

Constat : profiles.yml pointe vers ../data/warehouse.duckdb — ne fonctionne que
depuis dbt_project/.

Réponse :
- Business : Le pipeline est orchestré par Airflow qui contrôle le cwd.
  L'utilisateur final ne lance jamais dbt manuellement.
- Technique : Le BashOperator dans le DAG fait cd dbt_project && dbt run
  --profiles-dir . En production, on utiliserait des chemins absolus ou des
  variables d'environnement (DBT_PROFILES_DIR).
- Compromis : Acceptable pour un projet mono-repo où l'orchestrateur garantit
  le contexte d'exécution.


7. Streaming non intégré au pipeline batch
------------------------------------------

Constat : Le producteur/consommateur Kafka existent mais le pipeline
d'optimisation utilise l'API REST Binance.

Réponse :
- Business : Deux cas d'usage distincts. Batch : optimisation de portefeuille
  (quotidien, planifié par Airflow). Streaming : monitoring temps réel (klines +
  order book, continu).
- Technique : Le streaming écrit en zone Bronze (data/streaming/). Le batch lit
  la zone Bronze (data/raw/). Ce sont deux flux indépendants par design —
  architecture Lambda classique. L'intégration consisterait à faire lire le
  pipeline batch depuis les données streaming, ce qui nécessite une couche de
  réconciliation (deduplication, late arrivals).
- Compromis : La séparation batch/streaming est un choix architectural documenté,
  pas un oubli. La convergence vers un modèle Kappa est un axe d'évolution
  identifié.


8. Zéro test d'intégration (100% mocks)
----------------------------------------

Constat : ~1 000 occurrences de mock/patch dans les tests. Aucun test ne touche
une vraie API ou une vraie base.

Réponse :
- Business : Les tests doivent être rapides, reproductibles, et exécutables en CI
  sans infrastructure externe. Un test qui appelle Binance échoue si l'API est
  down ou si les données changent.
- Technique : Les mocks testent la logique métier (calculs financiers,
  optimisation, backtest). La validation end-to-end se fait via le script de
  démonstration (CLAUDE.md § Demo Script) qui exécute le pipeline réel. En
  production, on ajouterait des tests d'intégration dans un environnement dédié
  (Docker Compose + fixtures).
- Compromis : La pyramide des tests est volontairement orientée unitaire.
  1 200+ tests unitaires avec 0 flaky > 50 tests d'intégration fragiles pour un
  projet de certification.


9. Coverage non enforced
------------------------

Constat : Pas de seuil minimum dans la CI. Le badge indique ~55%.

Réponse :
- Business : L'objectif est de démontrer une couverture significative sur le code
  critique (pipeline, optimisation, API), pas d'atteindre un chiffre arbitraire.
- Technique : Les 55% couvrent le code source (src/). Les modules non couverts
  sont principalement des intégrations externes (Kafka, MinIO, Spark) testés par
  mocks. Les modules critiques (transform, optimize, backtest) sont à 90%+.
- Compromis : Un seuil de 80% global forcerait à écrire des tests triviaux pour
  du code d'infrastructure. Mieux vaut 90% sur le coeur métier que 80% dilué sur
  tout le repo.


10. Taux sans risque : incohérence crypto/trad
-----------------------------------------------

Constat : risk_free_rate = 0.05 utilisé partout, mais crypto annualise sur 365j
et trad sur 252j.

Réponse :
- Business : Le Rf de 5% est un proxy standard (taux souverain US). La
  comparaison crypto/trad utilise le même Rf pour assurer la comparabilité des
  Sharpe ratios entre les deux univers.
- Technique : Le Rf annuel est le même (5%). Ce qui diffère est le facteur
  d'annualisation de la volatilité : √365 pour crypto (marchés 24/7) vs √252
  pour trad (jours ouvrés). C'est financièrement correct — les deux rendements
  sont annualisés avant le calcul du Sharpe.
- Compromis : On pourrait ajuster le Rf au taux journalier (Rf/365 vs Rf/252)
  pour plus de rigueur, mais l'impact sur le classement des portefeuilles est
  négligeable.


Synthèse
========

 #  | Point              | Gravité  | Défense
----|--------------------|----------|------------------------------------------
 1  | Credentials        | Faible   | Contexte certif, pas de données sensibles
 2  | Annualisation      | Moyenne  | Correct en daily (cas par défaut)
 3  | Sharpe élevé       | Moyenne  | Période courte + in-sample, corrigé par backtest
 4  | Delta Lake mort    | Faible   | Implémenté, testé, activable par config
 5  | Spark local        | Faible   | Volume ne justifie pas un cluster
 6  | dbt chemins        | Faible   | Airflow contrôle le cwd
 7  | Streaming isolé    | Moyenne  | Architecture Lambda assumée
 8  | Mocks only         | Moyenne  | Pyramide unitaire + démo end-to-end
 9  | Coverage           | Faible   | 90%+ sur le coeur métier
10  | Rf crypto/trad     | Faible   | Financièrement cohérent

Posture recommandée : Ne jamais nier un compromis. Dire « c'est un choix
documenté dans l'ADR/la config, voici pourquoi, et voici comment on
l'améliorerait en production ». Le jury évalue votre capacité de jugement,
pas la perfection du code.
